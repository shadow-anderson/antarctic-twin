# Data Provenance

This project distinguishes three categories for every data point — **Real** (directly measured and archived), **Simulated** (generated by code, not measured), and **Derived** (computed from Real and/or Simulated inputs) — and every metric in the UI is tagged with one of these via `source` fields in API responses and the provenance registry. The canonical source of truth for these tags is `frontend/lib/provenance.ts` (the `PROVENANCE_REGISTRY` array); the generation mechanism behind each entry is implemented in `backend/app/api/stations.py`.

---

## Real data

### Weather observations (temperature, wind speed, atmospheric pressure)

**Registry keys:** `weather_temperature`, `weather_wind_speed`, `weather_pressure`
**Origin label:** "NCPOR/IMD AWS archive"

These three fields come from archived Automatic Weather Station (AWS) data collected by India's National Centre for Polar and Ocean Research (NCPOR) and the India Meteorological Department (IMD). The processed CSVs live at:

- `data/processed/maitri_clean.csv` — sourced from `data/raw/maitri_aws_imd.csv`
- `data/processed/bharati_clean.csv` — sourced from `data/raw/bharati_aws_iig.csv`

**Actual date ranges in the processed CSVs (verified by querying the files directly):**

| Station | Earliest observation | Latest observation |
|---------|---------------------|-------------------|
| Maitri  | 1985-01-01 00:00:00 | 2016-12-19 12:00:00 |
| Bharati | 2012-01-28 12:00:00 | 2016-12-31 23:00:00 |

**Selection rule in `get_station_current()` (lines 164–175 of `stations.py`):** the CSV is filtered to rows where `tempr`, `ap`, and `ws` are all simultaneously non-null, sorted descending by `obstime`, and the first (most recent) such row is returned. The three values are assigned `source: "real"` in the `WeatherBlock` response.

**This data is archival, not live.** The API returns the last recorded observation from a static CSV file; it is not connected to any real-time instrument feed. The `observation_time` field in the response is the timestamp of that archived row, not the current wall-clock time.

**Current `observation_time` values returned by the locally running API at time of writing this document:**

| Station | `observation_time` |
|---------|--------------------|
| Maitri  | `2016-12-19T12:00:00` |
| Bharati | `2016-12-31T23:00:00` |

These values were retrieved by calling `http://localhost:8000/stations/{station_id}/current` against the locally running backend process at the time this file was authored. Any future contributor should re-verify these by calling the endpoint directly, since the underlying CSVs could be updated.

### Station facts (coordinates, capacity, descriptions)

**Registry key:** `station_facts`
**Origin label:** "NCPOR station documentation"

Station names, coordinates, and descriptions are sourced from official NCPOR documentation. They are stored in two places in the codebase:

1. **Backend:** `STATIONS` dict in `stations.py` (lines 45–48) holds coordinates used for geographic display:
   - Maitri: lat −70.76, lon 11.73
   - Bharati: lat −69.41, lon 76.19

2. **Backend:** `_STATION_CAPS` dict in `stations.py` (lines 330–333) holds personnel capacities returned by `GET /stations`:
   - Maitri: summer 25, winter 25
   - Bharati: summer 47, winter 47

3. **Frontend:** `STATION_METADATA` in `frontend/lib/mockData.ts` (lines 7–27) and inline constants in `frontend/components/overview/OverviewPanel.tsx` (lines 84–124) also contain station facts used to populate the UI's hero card and profile section. See the **Known limitations** section for a specific inconsistency between these sources.

## Simulated data

The following metrics are **not measured**. NCPOR does not publicly expose live operational telemetry for power generation, fuel levels, or equipment condition at Maitri or Bharati. These values are generated entirely in code from hardcoded baselines plus a deterministic time-seeded jitter. The intent, stated in the module-level comment, is that any of these fields could be replaced by a real data feed without changing field names, shapes, or the `source` attribute — because `source` is a per-field attribute set individually on each `Metric` object, not a global mode switch.

### Energy telemetry (generation, consumption, diesel level)

**Registry keys:** `energy_generation`, `energy_consumption`, `energy_diesel_pct`
**Origin label:** "Seeded microgrid model"

**Baseline values** — hardcoded in `_BASE_ENERGY` (lines 56–71 of `stations.py`):

| Field | Maitri baseline | Bharati baseline |
|-------|----------------|-----------------|
| `generation_kw` | 142.0 kW | 187.0 kW |
| `consumption_kw` | 119.0 kW | 154.0 kW |
| `diesel_pct` | 61.0 % | 58.0 % |
| `food_days_remaining` | 68.0 days | 74.0 days |
| `diesel_days_remaining` | 42.0 days | 37.0 days |

**Jitter mechanism** — `_jitter(base, pct, seed)` (line 99) computes `base ± (base × pct/100)` using `random.uniform` seeded with a deterministic integer. The seed — `_time_seed(asset_id, station_id)` (line 106) — is `hash(f"{station_id}:{asset_id}:{slot}") & 0x7FFFFFFF` where `slot = int(utc_timestamp) // 180`. This means the seed changes every 3 minutes (180 seconds), but is identical for all calls within the same 3-minute window. The effect is that the numbers look like fluctuating telemetry but are deterministic and stable within any given window.

**Jitter bounds per field, as implemented in `get_station_current()` (lines 193–216):**

| Field | Jitter (± %) |
|-------|-------------|
| `generation_kw` | ±4% |
| `consumption_kw` | ±4% |
| `diesel_pct` | ±1.5% |
| `food_days_remaining` | ±1% |
| `diesel_days_remaining` | ±1% |

### Logistics reserves (food days, diesel days)

**Registry keys:** `logistics_food_days`, `logistics_diesel_days`
**Origin label:** "Seeded logistics model"

`food_days_remaining` and `diesel_days_remaining` are part of `_BASE_ENERGY` and share the same jitter mechanism described above (±1% bounds). They represent notional reserve levels, not readings from actual inventory systems.

### Asset telemetry (generators, battery, pumps, buildings)

**Registry key:** `asset_telemetry`
**Origin label:** "Seeded asset simulation"

All per-asset telemetry — health percentage, temperature, vibration, efficiency, runtime hours — is built in `_build_asset_detail()` (lines 1025–1232 of `stations.py`) from hardcoded per-asset baseline values stored in `_STATION_OFFSETS` (lines 896–977). There is a separate `_STATION_OFFSETS` entry for each of the 13 assets at each station (gen-01, gen-02, battery-sys, water-pump, water-storage, bld-main, bld-lab, bld-storage, log-food, log-diesel, log-medical, log-water, log-spares).

Each numeric telemetry field is jittered using the same `_jitter()` / `_time_seed()` mechanism, with a default jitter of **±3%** for equipment assets (health, temp, vibration, efficiency, runtime hours). The vibration field uses a ±5% jitter call (`_jitter(val, 5.0, ...)`) for generator and pump assets, as called from the inner `j()` closure on line 1047.

Logistics assets (`log-food`, `log-diesel`, `log-medical`, `log-water`, `log-spares`) have `telemetry_source: "derived"` set in their `AssetDetail` response, reflecting that their health figures are computed from inventory estimates rather than sensor readings.

### Comms link state

**Registry key:** `link_state`
**Origin label:** "Simulated demo control"

The satellite link connected/disconnected state (`GET /link/status`, `POST /link/toggle`) is held in an in-memory Python dict `_link_state` (line 309). It resets to `connected: True` on every process restart. It has no connection to any actual satellite link; it is a demo toggle for demonstrating the UI's degraded-comms behaviour.

## Derived data

### Anomaly flags

**Registry key:** `anomalies`
**Origin label:** "z-score vs NCPOR historical baseline"

Implemented in `_detect_anomalies()` (lines 677–729 of `stations.py`). The function:

1. Takes the **last row** of the processed CSV (sorted ascending by `obstime`, so `iloc[-1]`) — note this is the same record as the latest complete-row weather observation.
2. Builds a baseline lookup key of the form `"MM_HH"` (month, zero-padded; UTC hour, zero-padded) from that row's timestamp.
3. Looks up per-variable mean and standard deviation for that month-hour slot from `data/baseline_stats.json` (loaded once at module import into `_BASELINE`).
4. Computes z-score: `z = (observed_value - mean) / std`.
5. Flags the variable as anomalous if `|z| > _SIGMA_THRESHOLD` where `_SIGMA_THRESHOLD = 2.0` (line 658).

**Severity tiers** (from `_severity_from_z()`, lines 668–674):

| Condition | Severity |
|-----------|---------|
| `|z| >= 4.0` | `"high"` |
| `3.0 <= |z| < 4.0` | `"medium"` |
| `2.0 < |z| < 3.0` | `"low"` |

The baselines are derived from the same archived AWS data, so anomalies are computed against the historical distribution of the archival data itself — not against any live climatological reference.

### Depletion forecasts (diesel and food)

**Registry keys:** `forecast_diesel`, `forecast_food`
**Origin label:** "Computed from simulated inventory (linear burn)"

Implemented in `compute_forecast()` (lines 581–651 of `stations.py`). For each resource:

- **Diesel burn rate:** `burn_rate = 1.0 + max(0, (consumption_kw - generation_kw) / generation_kw)`. If consumption exceeds generation (an energy deficit), the burn rate is elevated above 1.0; if generation equals or exceeds consumption, burn rate is exactly 1.0 (nominal).
- **Food burn rate:** fixed at 1.0 (straightforward linear depletion, no power-linked acceleration).
- **Projection:** for each day `d` from 0 to 30, `days_remaining(d) = max(0, current_days_remaining - d × burn_rate)`.

**Threshold definitions** (from `WARNING_DAYS` and `CRITICAL_DAYS` constants, lines 604–605):

| Label | Threshold |
|-------|-----------|
| `"warning"` | ≤ 15.0 days remaining |
| `"critical"` | ≤ 7.0 days remaining |

The `projected_day` field in each threshold crossing reports the first day in the 30-day projection at which `days_remaining` falls to or below the threshold.

Because the input (`current_days_remaining`) is itself a simulated value (see § Simulated data above), the forecast is a derivation of simulated state, not a derivation of real inventory data.

### What-if scenario results

**Registry key:** `whatif`
**Origin label:** "Scenario multipliers on simulated state"

Implemented in `compute_whatif()` (lines 369–573 of `stations.py`). Three scenarios are supported, each defined by physics multipliers in `_SCENARIO_PARAMS` (lines 341–361):

| Scenario | `generation_multiplier` | `consumption_multiplier` | `diesel_burn_multiplier` | Other |
|----------|------------------------|--------------------------|--------------------------|-------|
| `generator_failure` | 0.55 | 1.0 | 1.30 | — |
| `blizzard` | 0.85 | 1.25 | 1.20 | — |
| `resupply_delay` | 1.0 | 1.0 | 1.0 | `resupply_delay_days: 45` |

The computation:
1. Fetches the station's current simulated state via `get_station_current()`.
2. Applies multipliers: `new_gen = cur_gen × gen_mult`, `new_con = cur_con × con_mult`.
3. Adjusts diesel days: `new_diesel_days = cur_diesel_days / burn_mult` (except `resupply_delay`, which keeps current days and instead models a 45-day delay before resupply).
4. Computes `days_until_critical = max(0, round(new_diesel_days × 0.15))` — the projected number of days until diesel reserves cross the 15% operational threshold.
5. Determines urgency verdict: `"urgent"` if `days_until_critical ≤ 3`, `"warning"` if `≤ 7`, otherwise `"monitor"`.
6. Generates timeline events and recommendations from the computed numbers, not from static canned text.

## Known limitations

- **Weather data is archival, not live.** The processed CSVs end at 2016-12-19 (Maitri) and 2016-12-31 (Bharati). Every API call returns readings from that date, not from today. There is no live AWS feed.

- **Deployed state should be verified before every demo.** The live Render deployment may lag behind the `main` branch. The deployed and repo states have drifted before in this project. Before a demo or judging session, confirm that the deployed service is running the same commit as the repo.

- **Inconsistency between `mockData.ts` and `OverviewPanel.tsx` for Maitri's established year and elevation.** As of the current code:
  - `frontend/lib/mockData.ts` (line 15) has `established: 1989` and `elevation: "117 m"` for Maitri.
  - `frontend/components/overview/OverviewPanel.tsx` (lines 98, 101) has `established: "1988"` and `elevation: "≈50 m"` for the same station.
  - The two values are not reconciled; the UI hero card renders from `OverviewPanel.tsx`'s inline `stationDescriptions` object (using "1988" and "≈50 m"), while `STATION_METADATA` in `mockData.ts` (using 1989 and "117 m") is used for the coordinates chip and station ID pill.
  - Additionally, for Bharati, `mockData.ts` states `capacity: 47` while `OverviewPanel.tsx` displays `capacity: "72 personnel"` (the total including summer-camp overflow). The backend API (`_STATION_CAPS`) returns summer/winter: 47. The capacity figure shown in the hero card (72) is not what the API returns.
  - These discrepancies should be resolved by picking one authoritative source (NCPOR documentation) and propagating it consistently.

- **CORS is open to all origins.** `backend/app/main.py` sets `allow_origins=["*"]` with an inline comment that reads "allow all origins for hackathon (tighten in production)". Any origin can make credentialed cross-origin requests to the API in the current configuration.
